# M17 - AI layer (CFO copilot): results and limitations

**Run mode.** The first set of results below was produced WITHOUT a live LLM (no credentials at the time);
a live run via Ollama cloud (`gemma4:31b-cloud`, free tier) is reported in the next section. Offline results: the text-to-SQL agent used the deterministic `TemplateGenerator` baseline, RAG used offline LSA embeddings, commentary used template
drafts, and extraction was tested with a mock provider. The live paths (`LLMGenerator`, `Gateway("anthropic"|"openai"|"ollama")`,
`rag.answer(gateway=...)`, `llm_extract.extract`) are implemented and unit-tested only through the mock. 

## Live text-to-SQL run (Ollama cloud, gemma4:31b-cloud, untuned prompt)
* **43/69 = 62.3% execution accuracy**, coverage 100%, mean latency 2.3 s per call. By category: scenario 10/10, **hard 9/12 (baseline 0/12)**, allocation 6/9, rank 3/6, lookup 12/23, stats 3/9.
* The simple-lookup misses are mostly semantic mismatches with the gold SQL (e.g. choosing the quarterly `fee_yield_bps` column instead of `fee_yield_t4q_bps`, or not skipping NULL latest quarters), not syntax errors. A better schema prompt (metric glossary, 'latest = latest non-null T4Q') would likely lift this; it was deliberately NOT tuned on the eval set.
* Larger Ollama models (kimi-k3, glm-5.3, deepseek-v4.1) returned HTTP 402 (need paid credits). Only the free-tier model was evaluated; Claude not evaluated. Reproduce: `uv run python -m assetlens.ai.live_eval ollama gemma4:31b-cloud` (needs `OLLAMA_API_KEY` in `.env`).

## Text-to-SQL agent (offline baseline) (LangGraph: generate -> validate -> execute -> answer)
* Validator (sqlglot AST): single SELECT only, allow-listed marts, no schema-qualified or file/system functions, <= 3 joins, no cross joins, forced `LIMIT 1000`; executes on a read-only connection with external access disabled.
* **Adversarial set: 17/17 rejected** (DDL, DML, multiple statements, file reads, `information_schema`, disallowed tables, cross join, attach/pragma/install).
* **Eval set: 69 finance questions with executed gold SQL.** Baseline execution accuracy **57/69 = 82.6%** (coverage 91%): lookup 23/23, rank 6/6, scenario 10/10, allocation 9/9, stats 9/9, **hard (multi-step / paraphrase) 0/12**. The easy categories are template-shaped, so they flatter the baseline; the 0/12 on hard questions is the number to beat with an LLM generator.

## RAG over filings
* 1,758 chunks from the latest 10-Qs (GS, TROW, IVZ, MS, JPM, BEN, BLK) and four earnings releases; hybrid = reciprocal-rank fusion of BM25 and LSA dense retrieval; answers cite ticker, form, **accession number and section**.
* 20-question retrieval eval (top-5 contains an expected phrase): BM25 0.90, dense LSA 0.80, **hybrid 0.90**. Hybrid did not beat BM25 here; the metric is crude and the sample small.

## Commentary with numeric guardrail
* Every number in generated text is matched to a warehouse fact (rounding-aware, each fact usable once; years/quarter tags ignored).
* 10 clean template drafts all pass; **250 seeded wrong-number drafts (one number changed by 8-60%): 250/250 blocked.** Limitation: a fabricated number that exactly equals an unused fact value would pass; single-use matching reduces but cannot remove this.

## LLM-assisted extraction (M2 fallback)
* Pydantic schema (begin, flows, market, other, end, unit, source rows) + closure validator + grounding check (every number must occur in the source table) + review queue CSV. Tested: valid extraction queued as `pending_review`; hallucinated numbers and non-closing roll-forwards rejected; nothing is released without `reviewed` and `decision == approve`.

## Gateway
* `ai/gateway.py`: Claude / OpenAI / Ollama / mock behind one interface; latency, tokens and cost logged to DuckDB `llm_calls` (prices are placeholders to update).
